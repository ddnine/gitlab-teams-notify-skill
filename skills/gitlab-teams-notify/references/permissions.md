# 权限与可靠性扩展

## 发送前访问校验

静态映射只证明曾经绑定过身份。历史创建者退出项目后仍可能在事件中出现，默认模板不能证明其仍可访问事项。如果用户要求防止这一泄露，在发送卡片前增加校验，失败时不发送事项内容。

先确定 GitLab 版本、事项类型、公开性、机密标记、用户状态和有效成员关系。`members/all` 可用于合并直接、继承与受邀组成员关系，但“是项目成员”既不是访问公开事项的必要条件，也不足以证明能访问所有机密事项。查询令牌自身能读事项也不证明收件人能读。

对受控的私有项目，可选择更保守的规则：只给当前有效、非过期、非受限成员发普通事项；对机密事项同时核对版本对应的角色及作者 / 负责人例外。检查结果与用户 ID 关联，避免使用过期缓存。无法准确判断时拒绝发送并只告警 ID 与原因，不把标题或回复泄露到告警。

若要求准确支持所有访问例外，需要 GitLab 提供的适当权限判定能力、用户授权访问或受控中间服务。普通项目 Maintainer 不具有管理员 `sudo` 能力。不要假装用服务账号 GET issue 就完成了用户权限校验。即时权限仍有检查与发送间的时间差，已发送卡片也不会随着权限撤销自动消失。

Power Automate 中调用通用 HTTP 等动作可能需要 Premium 许可；不要未经说明新增收费连接器、管理员凭据或第三方接收服务。中间服务应校验输入、保护凭据，并把许可判断落实在真正发送之前，不能只接收一个请求传来的 `can_access=true`。

参考：[有效项目成员](https://docs.gitlab.com/api/project_members/)、[机密事项访问规则](https://docs.gitlab.com/user/project/issues/confidential_issues/)、[令牌范围](https://docs.gitlab.com/security/tokens/access_token_scopes/)。

## 来源认证与去重

项目 ID、URL 前缀和成员映射都是路由条件，不能防止持有回调链接的人伪造请求。按目标 GitLab 版本选择 Secret Token 或签名验证；签名验证必须使用官方规定的原始请求体、时间戳和算法。不能把生成器的离线路由测试当作来源认证测试。保持 HTTPS 与证书校验。

模板的 `union` 只消除单次运行内的重复邮箱。网络重试或 Webhook 重送仍可能产生多次通知。需要跨运行保证时，使用官方事件 / 投递标识或稳定事件字段生成键，并持久化“事件 + 收件人”的处理状态。先检查再写入而无原子约束会有并发竞争；发送成功和记账之间仍需处理故障恢复。

参考：[GitLab Webhook 安全、标识与重试](https://docs.gitlab.com/user/project/integrations/webhooks/)。

## 告警与维护所有权

默认使用现有 Teams 连接发给连接所有者，告警只包含项目标签、失败摘要和运行链接。连接本身失效时告警也可能失败；触发器之前的网络故障或流程完全未启动也不在动作 runAfter 覆盖范围内。

独立邮箱、监控通道或定时巡检可以补足这一点，但不能从“失败告警”推断用户同意新增 Outlook 权限。遵循用户选定的通道，并如实说明覆盖范围。平台自带失败邮件不保证覆盖每一种失败。

添加流程共同所有者能改善维护连续性，但不等于移交连接凭据。移交前检查新所有者权限、连接和测试结果，再停止旧路径，避免双重发送。

参考：[错误处理](https://learn.microsoft.com/en-us/power-automate/guidance/coding-guidelines/error-handling)、[共享流程与连接](https://learn.microsoft.com/en-us/power-automate/create-team-flows)。
