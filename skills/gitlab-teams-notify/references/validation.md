# 验证与排障

## 离线验证

生成器可读取自定义模板之后的 JSON：

```sh
python3 scripts/build_flow.py --config <私有配置> --out <私有目录> --event <事件 JSON>
```

`simulation.json` 包含去重后的收件人邮箱和卡片对象，仅写入私有目录。离线模拟与生成表达式共享同一条收件人规则，但它不是 Microsoft 运行引擎，不能证明连接、租户权限或实际卡片渲染成功。

应覆盖：

| 输入 | 预期 |
| --- | --- |
| 新建事项，有负责人 | 通知映射中的负责人 |
| 新建事项，无负责人 | 不通知 |
| 改派新增负责人 | 只通知新增 ID |
| 原负责人改用户名，ID 不变 | 不重复通知 |
| 用户名相同，新增 ID 不同 | 依据 ID 通知 |
| 新回复，负责人也是创建者 | 一份卡片 |
| 新回复 @ 已映射用户，该人并非负责人或创建者 | 通知被 @ 的用户 |
| 新回复同时 @ 多个账号，映射到同一邮箱 | 一份卡片 |
| @ 用户名大小写不同、结尾有句号 | 匹配完整用户名 |
| 邮箱、相似用户名、群组路径、常见代码片段里的 @ | 不按个人 @ 通知 |
| 缺少 note_body 的旧负载 | 保留原有负责人和创建者通知 |
| 发言者有多个 GitLab 账号共用邮箱 | 排除该邮箱的所有账号 |
| 未映射发言者 | 正常通知已映射目标，无空数组错误 |
| 系统备注、编辑回复、MR 评论、其他项目 | 不通知 |
| 标题有引号、反斜线、换行或表达式样式文字 | 保留文本，JSON 有效 |

## 云端验证

先看已有运行，避免重复发送。需要主动测试时使用独立测试流程或明确限定为操作者自己的映射；不要临时把同事映射到其他人，也不要创建真实业务事项来制造测试事件。

验证 @ 时，使用未知的测试操作人和创建者、空负责人数组，仅在正文 @ 操作者自己，证明结果来自 @ 分支。再检查重复身份、自我 @、编辑回复和边界负例。离线测试可使用 `xmllint` 执行同一条 XPath，但仍需云端验证 XML 转换和表达式类型。若仅通过合成 Webhook 验证，应明确记录尚未验证真实 GitLab 回复事件，不能把入口 202 当作完整验收。

成功判据应同时包括：保存后的配置正确、入口接受、Recipients / foreachItems 正确、发送动作成功、卡片内容和链接正确。至少确认正常运行、零收件人运行和失败路径；真实接收仍以 Teams 可见卡片为准。

正常运行和零收件人时 `FailureAlert` / `MarkFailed` 应跳过。受控测试中可以用错误类型的历史负责人数组验证上游失败路径，或用非法卡片字段验证发送失败路径。只允许对隔离测试运行做此操作，告警只发给操作者；不要通过吊销生产凭据或移除生产成员来制造故障。

失败告警成功后，整体运行仍应为 Failed。不要为了避免红色状态去移除 MarkFailed；红色状态用于运维发现通知故障。

## 排障顺序

1. GitLab 没有投递：检查事件勾选、Webhook 禁用状态、可达性和证书。
2. 入口有 202，但没有卡片：打开对应 Power Automate 运行，查 Recipients 和循环内容；随后查 PostCard 返回，而不是仅看触发器。
3. 收件人不正确：检查数字 ID 类型、统一 MemberMap、历史负责人投影以及邮箱归一化。未知发言者不得使 `first()` 读取空数组。
4. 表达式原样显示：确认 UI 使用表达式模式；数组和对象不要变成普通字符串。
5. 卡片失败：查看具体连接器错误；检查字段类型、长度、租户策略和连接身份。修正原因后只重试受影响的收件人，限制次数。
6. 浏览器控制超时：重新读取当前页面并定位当前动作，确认异步面板已加载。用户切换标签可能影响原生操作；必要时协调一个短暂编辑窗口。不要把控制超时说成服务断网，也不要盲目重复点击“保存”或“发送”。

运行详情与截图可能含用户、标题和签名 URL，保留在私有维护位置，不附到通用 skill 仓库。
